## 발견 사항

### 1. 응답 구조 동일

다세대·연립의 응답 필드가 아파트와 **바이트 단위로 동일**하다:

```
page_no, list_size, total_cnt, year, reg, eub, apt_code, dong_code, ho_code,
apt_name, dong_name, ho_name, notice_date, notice_date_name, full_road_name,
short_addr_name, full_addr_name, priv_area, notice_amt, ktown_ho_seq, ...
```

가격 필드: `notice_amt` (공백 패딩 문자열, 예: `"     172,000,000"`).
기존 `normalizeHistory(rows, { date: 'notice_date_name', price: 'notice_amt', area: 'priv_area' })`가 그대로 동작한다.

### 2. 동명 "동명없음"

다세대는 동이 하나인 경우가 많고, 동 이름이 `"동명없음"` 또는 건물 유형명(`"다세대주택"`)으로 나온다.
→ UX에서 동명이 `"동명없음"`이면 동 선택 UI를 생략하거나, 자동 선택하는 것이 자연스러움.

### 3. 단지명에 지번 접두사

GR3처럼 단지명이 `"(1439-12) 서초동다세대주택(PLUSHOUSE)"` 형태로 지번을 포함하는 경우가 있다.
기존 `normalizeComplexName`의 `COMPLEX_LOT_PREFIX_PATTERN`이 이미 `(지번)` 접두사를 제거하므로 매칭에 문제없다.

### 4. 0건 반환 ≠ 장애

`searchApt.search`가 빈 배열을 반환하면 해당 필지에 공동주택이 등록되지 않은 것이다 (다가구주택 등 개별주택일 수 있음).
프로브에서 방배동 447-12, 잠실동 178-4가 0건 — 다가구(개별주택)일 가능성.
→ 빈 성공 응답과 CAPTCHA/장애는 반드시 구분해야 한다 (계획 문서 참조).

### 5. 실거래가 API (RTMSDataSvcRHTrade) 정상 동작 확인

검증일: 2026-08-13. `fetchTradeDataset('rowhouse', ...)` 기존 코드로 호출.

| 구 | 기간 | 거래 건수 |
|---|---|---|
| 강남구 | 2026년 7월 | 70건 |
| 강남구 | 2026년 6월 | 87건 |
| 서초구 | 2026년 7월 | 73건 |

골든 케이스 매칭: **역삼동 795-10 역삼그린빌리지** — 2026-06-14 매매 1,460,000,000원 발견.

응답 필드가 아파트 실거래가와 동일 구조:
- `buildingName`: `aptNm` 대신 `mhouseNm` → 기존 `normalizeTrade`의 `first(item, ['aptNm', 'mhouseNm', 'offiNm'])`이 이미 처리
- `legalDongName`, `jibun`, `dealAmount`, `exclusiveArea`, `floor` 모두 동일

### 6. T0 추가 검증 (2026-08-14)

**GR2 거래 매칭**: 역삼동 693번지 거래 0건 (최근 13개월 거래 없음). 매칭 로직 직접 검증 불가.
다만 같은 이름 패턴(`현대빌라(지번)`)의 다른 건물 거래 16건 확인 — 거래 데이터의 `mhouseNm`에도
지번 suffix가 붙는 패턴 확인됨: `현대빌라(227-1)`, `현대빌라(89)`, `현대빌라A`.

**다중 빌라 필지**: 8개 후보 필지 + 거래 데이터에서 같은 PNU에 공동주택 2개+ 등록된 케이스 미발견.
→ 실제로 드문 케이스. 기존 `matchTrade` 다중 후보 분기로 충분.

**GR3 거래**: 서초동 1439번지 거래 0건 (최근 13개월). 5호짜리 소규모 다세대 — "거래 없음"이 기대값.

### 7. 아파트/연립 구분 불가 확인

API 응답에 건물 유형(아파트/연립/다세대)을 나타내는 필드가 **없다**.
→ `'rowhouse'` AssetKind를 추가하지 않기로 한 결정을 재확인.
