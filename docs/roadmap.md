# 구축 로드맵

엔지니어링 규칙은 [AGENTS.md](../AGENTS.md)에 있다. 이 문서는 **무엇을 어떤 순서로
만드는지**만 정의한다. **최종 형태와 그 이유는 [product-vision.md](./product-vision.md)에 있다.**

각 Phase는 여러 Codex 태스크로 쪼개 디스패치한다. Phase 전체를 한 태스크로 주지 않는다.

> **P0~P8은 3단계(취득·보유·처분) 중 보유·처분만 덮는다.**
> 취득세, 지역자원시설세, 농지·자경농지, 특수관계인 증여추정, 상담 연결은
> 아직 어느 Phase에도 없다. 공백 목록은 [product-vision.md §6](./product-vision.md).
> **Phase 번호를 붙이기 전에 §7의 확인 사항에 답이 필요하다.**

---

## 의존 관계

```
P0 룰 엔진 ──────────────────────┐
                                 ├─→ P4 보유세 ─┐
P1 데이터 파이프라인 → P2 지도 ───┤              ├─→ P6 시뮬레이션 → P7 잔여 세제 → P8 상가·토지
                                 │              │
P3 공시가격 ─────────────────────┴─→ P5 양도세 ─┘
```

**실행 순서 (Wave) — 이 표가 순서의 SSOT다**

**Phase 번호는 식별자이지 순서가 아니다.** P9(취득세)는 나중에 신설돼 번호가 뒤지만
Wave 4에서 실행한다. 기존 번호를 다시 매기지 않는다 — 다른 문서 20여 곳의 참조가
어긋나면 그게 R5 위반이다.

| Wave | Phase | 상태 | 비고 |
|---|---|---|---|
| 1 | **P0, P1, P3** | P0·P1 완료 / P3 Worker 완료 | 서로 독립 |
| 2 | **P2** | 완료 (P2-3~6 개선 남음) | P1 필요 |
| 3 | **P4 보유세** → **P5 양도세** | 착수 전 | ← **A안: 주택 3단계를 순서대로** |
| 4 | **P9 취득세** | 신설 | 주택 3단계 완결 |
| 5 | **P6 시뮬레이션** | | P4·P5·P9 필요 |
| 6 | **P7 잔여 세제** | | |
| 7 | **P8 토지·상가 + 좌측 사이드바** | | 주택 완결 후 |

P3은 Worker 계층까지 Wave 1에서 만들었다. UI 통합만 P4에서 한다.

**P0~P7·P9가 주택 전용이다.** A안에 따라 **주택 3단계(보유·양도·취득)를 먼저 끝내고**
P8에서 토지·상가로 넓힌다. 그래도 주택 전용 가정을 코드에 박지 않도록
AGENTS.md §4에 자산 유형 규약을 두었다.

## P0 — 세법 룰 엔진

**목표** 외부 데이터에 의존하지 않는 순수 계산 계층. 이 프로젝트의 심장.

**산출물**
- `src/rules/` — 연도별 룰 테이블 (`2026`=현행, `2027`, `2028`, `2029`)
  - 재산세: 공정시장가액비율, 세율표, 지방교육세, 도시지역분
  - 종부세: 과세대상 기준, 기본공제, 공정시장가액비율, 세율표, 재산세 공제, 농특세
  - 양도세: 기본세율, 단기 중과세율, 장기보유특별공제, 기본공제
- `src/rules/rounding.ts` — 공용 반올림 함수 (R5: 단 하나만 존재)
- `src/holding/calc.ts` — 보유세 계산 (단일 주택 + 합산)
- `src/transfer/calc.ts` — 양도세 계산
- `tests/` — 골든 케이스 테스트

**검증**
- `docs/golden-cases.md`의 기대값과 **1원 단위까지** 일치
- 경계값 전부 포함: 9억 / 12억 / 14억 / 25억 / 30억, 보유 2·3·10·15년, 거주 2·10년
- 모든 세법 값에 개편안 페이지 출처 주석

**선행** 없음. 단, `docs/tax-rules-spec.md`와 `docs/golden-cases.md`가 먼저 있어야 한다.

## P1 — 데이터 파이프라인 (단지 마스터)

**목표** 지도가 읽을 D1을 채운다. **이 UX의 관문.**

> **실거래가는 선적재하지 않는다 (2026-08-04 변경).** 라벨을 단지명으로 확정하면서
> 지도가 실거래가를 필요로 하지 않게 됐다. 실거래가는 **사이드바에서 단지 하나를 열 때
> 온디맨드로 조회**하고 결과만 캐시한다. 근거는 P2 라벨 설계 절 참조.

**산출물**
- `migrations/` — D1 스키마
  - `complex` — 단지코드 PK, 단지명, 법정동·도로명주소, 법정동코드, 사용승인일,
    동수, 세대수, lat, lng. **lat/lng 인덱스 필수**
  - `trade` — 단지코드 FK, 거래일, 거래금액, 전용면적, 층. **온디맨드 조회 결과 캐시**
- `scripts/ingest-complexes.ts` — 국토부 단지 목록 수집 + 카카오 주소·좌표 확보
- `worker/complex/` — bbox 조회 API. 단지 위치·기본정보만 반환

**검증**
- 적재가 **원자적**이고 멱등하다 (R4-a). 검증 미달 시 기존 데이터 유지
- 단지 매칭률을 로그로 남긴다. 매칭 실패 건이 조용히 사라지지 않는다
- bbox 조회가 마커 상한을 넘지 않는다
- 지오코딩 실패 건이 전체 실패로 번지지 않는다

**선행** 없음.

**주의**
- 카카오 지오코딩은 배치 전용. 런타임 호출은 반려
- 검증은 좌표를 `coord2regioncode`에 넣어 받은 **법정동 코드를 `bjdCode`와 직접 비교**한다.
  주소 문자열 비교는 시+구 결합 표기(`안양동안구`)와 세종 2단계 주소에서 반복 실패했다

## P2 — 지도 + 사이드바

**목표** 지도를 띄우고, 단지명 라벨을 얹고, 클릭하면 사이드바가 열리는 데까지.

**산출물**
- `src/map/` — 카카오맵 SDK 로딩, bbox 기반 라벨 로딩, 줌 레벨 정책, 겹침 처리
- `src/map/ComplexLabel` — `kakao.maps.CustomOverlay` 기반 단지명 라벨
- `src/map/constants.ts` — 최소 표시 줌 레벨, 마커 상한 (R2)
- `src/sidebar/` — 단지 기본정보 + **실거래가 온디맨드 조회** + 연도별 평균가 차트
- `worker/trade/` — 단지 1개 실거래가 조회 (XML 파싱·해제 거래 제거·단지 매칭)
- `src/search/` — 단지 이름 검색 (`services.Places`)

**API 분리 — bbox는 위치만, 가격은 단지 단위**

```
GET /api/complexes?south=&north=&west=&east=   → 위치 + 단지 기본정보 (라벨용)
GET /api/complexes/:complexId/trades            → 그 단지의 실거래가 (사이드바용)
```

`ComplexSummary`에서 **`latestTrade`를 제거한다.** 라벨이 단지명이 된 이상 bbox 응답에
가격이 실릴 이유가 없고, 실으면 화면당 수백 건의 불필요한 조회가 따라온다.

실거래가는 **사이드바를 열 때 그 단지만** 조회한다. 단지 하나면 원천도 1개(아파트)로
충분해 13개월 × 13회, 약 1초다. 결과는 `trade` 테이블에 캐시해 재방문 시 즉시 응답한다.

> 부동산114도 `/props/gis`(위치)와 `/props/gis/sales`(가격)를 나눠 부른다. 다만 그쪽은
> 라벨에 가격을 띄우므로 가격도 bbox 단위다. 우리는 라벨이 단지명이라 **가격을 단지
> 단위로 더 좁힐 수 있다.**

**검증**
- 전국 줌에서 라벨을 전부 뿌리지 않는다. 일정 줌 이상에서만 표시
- 지도 이동·확대 시 요청이 디바운스된다
- 라벨이 서로 겹쳐 읽을 수 없는 상태가 되지 않는다
- SDK 키가 소스에 박혀 있지 않다 (R2)

**선행** P1

**SDK 사용법은 [kakao-map-reference.md](./kakao-map-reference.md)에 정리했다.**
공식 샘플 77개를 전수 조사한 결과이며, 채택/미사용 판정과 주의사항이 있다.

**라벨 설계 — 단지명 (2026-08-04 확정)**

```
┌──────────────┐
│  은마아파트   │  ← 단지명만
└──────▼───────┘
```

부동산114는 `가격 + 평형`을 띄우지만 **우리는 단지명만 띄운다.**

**근거.** data.go.kr 실거래가는 `법정동코드 × 거래년월` 단위로만 조회된다. 지도 화면
하나가 시군구 2~3개를 걸치므로 라벨에 가격을 띄우려면 **이동할 때마다 약 117회**
(시군구 3 × 13개월 × 3원천) 호출해야 한다. 일일 한도 10,000이면 **85번 이동에 소진**된다.

전량 선적재로 피할 수는 있으나, 그러면 대부분 조회되지 않을 전국 데이터를 받아
정기 갱신까지 떠안는다. **실거래가는 사이드바에서 단지 하나를 열 때만 필요하다.**

- 라벨은 단지명. `실거래가 없음` 같은 구분 표시가 불필요해진다
- 좌표가 없는 단지(5.2%)는 지도에 없고 **검색으로 도달**한다

**겹침 해결 — 레벨별 하이브리드**

`MarkerClusterer`는 `Marker` 전용이라 `CustomOverlay` 라벨에 걸리지 않는다. 그래서:

| 레벨 | 표시 |
|---|---|
| 확대 | `CustomOverlay` 단지명 라벨 |
| 축소 | **법정동 집계 라벨** → `청담동 18단지` |

`chickenClusterer` 샘플의 `calculator` + `texts` + `styles` 조합이 좌표 근접 클러스터의
패턴이지만, **P2-3에서 법정동 집계로 교체한다** (아래).

**P2-3 — 축소 라벨을 법정동 단위로 (2026-08-05, 호갱노노 분석 결과)**

현재 구현(`src/map/ComplexMap.tsx`)은 카카오 `MarkerClusterer`로 묶어 `123개 단지`를
띄운다. 좌표 근접도로만 묶으므로 **이름이 없다** — 축소 상태에서 사용자가 실제로 하는
일("우리 동네 어디지")에 답하지 못한다.

호갱노노는 같은 자리에 `청담동 24.5억`을 띄운다. 서버가 법정동으로 집계해 내려준다
([hogangnono-analysis.md §2](./hogangnono-analysis.md)).

우리는 `complex.legal_dong_code`(10자리, NOT NULL, 인덱스 보유)가 이미 있어
**외부 API 호출 0회**로 같은 것을 만든다. 실측 — 강남·광진 일대 한 화면에서
단지 254개가 **동 라벨 24개**로 축약된다 (자양동 45 · 삼성동 26 · 역삼동 24 · 논현동 19).

- 라벨은 `{동명} {N}단지`. **가격은 넣지 않는다** — 실거래가는 온디맨드 확정이다
- 동 이름은 지오코딩 시 카카오 `region_3depth_name`을 저장해 얻는다.
  `scripts/lib/kakao-complex-search.ts`가 지금은 `code`만 뽑고 이름을 버리는데,
  **같은 응답에 이미 들어 있다.** 프로덕션 적재를 한 번 더 돌려야 하므로 추가 호출 0회
- `legal_address` 파싱은 쓰지 않는다. 99.7%까지 맞지만(2,971개 중 2,963개) 휴리스틱을
  코드에 남기게 되어 R2에 어긋난다

**P2-4 — bbox 응답 최소화**

`worker/complex/bbox.ts`는 지금 단지당 10개 필드를 보낸다. 라벨에 필요한 건
`complex_id, name, lat, lng` 넷뿐이고, 나머지 6개는 **현재 아무 데도 안 쓰인다** —
사이드바는 `worker/complex/catalog.ts`로 상세를 따로 받는다.

실측(같은 뷰포트, 254개): 83.8 KB → **29.2 KB (65% 감소)**.

`ComplexSummary`를 읽는 곳은 `src/map/ComplexLabel.ts`와 `src/map/ComplexMap.tsx`
둘뿐이고, 둘 다 나머지 6개 필드를 참조하지 않는다(확인함).
`ORDER BY household_count DESC`는 유지한다 — SELECT에서 빠져도 정렬은 동작한다.

**P2-5 — 검색 결과에 동명 병기**

전국 단지명은 중복이 흔하다. `은마`만 해도 대치동·덕천동·서신동·구암동 네 곳이다.
단지명만 보여주면 어느 것인지 알 수 없다. 호갱노노 제안 목록은 `{동명} {단지명}`이다:

```
대치동 은마    덕천동 은마    서신동 은마    구암동 은마
```

동명은 P2-3에서 저장하는 값을 그대로 쓴다. **검색 로직은 바꾸지 않는다** — 우리 정확·
접두 매칭이 호갱노노의 퍼지 매칭보다 낫다(`대치동 316` → 은마가 나온다. 그쪽은 못 찾고
안산 그린빌16단지를 준다. [hogangnono-analysis.md §7](./hogangnono-analysis.md)).

**P2-6 — 평균가 차트의 평균 정의를 밝힌다**

연도별 평균가 차트가 지금 **전 거래를 단순 평균**한다. 저층·이상치가 그대로 섞인다.

호갱노노는 저층을 평균에서 빼고 화면에 이유를 적는다 — *"저층이기 때문에 평균 계산에서
제외됐습니다. 최고층이 10층 미만은 1층, 10층 이상은 3층까지를 저층으로 판단합니다."*

제외 규칙을 넣을지는 결정 사항이다. **다만 무엇을 평균했는지는 반드시 표시한다.**
세금 계산기에서 근거 없는 숫자를 보여줄 수 없다는 §4 계산 결과 규약과 같은 이유다.

**주의**
- 지도 레벨은 **작을수록 확대**다. 부등호 방향을 틀리기 쉽다
- `bounds_changed`는 드래그 중 연속 발생한다. `idle` 또는 디바운스 필수
- 사이드바 토글로 컨테이너 폭이 바뀌면 `map.relayout()` 호출
- 차트는 React용 라이브러리를 쓴다 (`vue-chartjs` 아님)

> 않는다** — 이름을 알고 찾는 것이기 때문이다.
>
> 같은 API라도 **"이름으로 찾기"는 되고 "영역을 빠짐없이 나열하기"는 안 된다**(측정:
> 강남 bbox `total_count` 2,254 vs `pageable_count` 45). 지도 마커는 D1 bbox 조회를 쓰고,
> 이름 검색만 카카오를 쓴다.

> `basicClusterer`·`addClustererClickEvent` 샘플이 있지만 **우리 라벨에는 못 쓴다.**
> `MarkerClusterer`는 `Marker`만 받는다. 낮은 줌에서는 라벨 대신 `Marker`로 전환해
> 클러스터러를 쓰는 하이브리드 방식은 가능하니, 필요하면 그때 검토한다.

## P3 — 주소→PNU + 공시가격

**목표** 단지·동·호를 특정해 공시가격을 가져온다.

**산출물**
- `worker/ldong/` — 법정동코드 KV 캐시, 주소→PNU 오프라인 변환
  (`iros-property-lookup`에서 이식)
- `worker/realty-price/` — 공동주택가격·개별주택가격 조회 (이식)
- `src/sidebar/UnitPicker` — **동/호 드롭다운** (P2 이후 통합)

**검증**
- 같은 단지에 대해 전년·당년 공시가격을 모두 가져온다
- 조회 실패와 "자료 없음"이 구분된다 (R4-b)
- 레이트리밋을 지킨다

**선행** Worker 계층은 없음. UI 통합은 P2.

**주의**
- **공시가격은 동/호를 특정해야만 조회된다.** realtyprice.kr이
  `searchApt.search`(동 목록) → `searchApt.search`(호 목록) →
  `townPriceListPastYearMap.search`(가격) 순으로 타고 들어가는 구조다.
  동/호 없이 단지 대표 공시가격을 얻을 방법은 없다 — 층·향·면적마다 다르기 때문이다
- 동/호 **목록을 API가 주므로 드롭다운으로 제공**한다. 사용자가 타이핑하게 하지 않는다
- **개별주택(단독·다가구)은 동/호가 없다.** 필지 단위라 주소만으로 조회된다.
  "공동주택은 동/호 필수, 개별주택은 주소만"
- `townPriceListPastYearMap.search`가 이름·반환형태상 **과거 연도 가격을 함께 주는 것으로
  보인다.** 사실이면 연도 파라미터화가 불필요해진다. **실제 응답을 찍어 먼저 확인할 것**

**P0에서 넘어온 제약 — 해소 결정**

목록에는 본인에게 과세되는 물건만 담고, `householdHomeCount`는 세대 소유 주택 수의
독립 입력으로 둔다. 근거는 [세법 명세 §3.6](./tax-rules-spec.md#36-공동명의-지분-안분)과
[§3.7](./tax-rules-spec.md#37-주택-수-판정)을 따른다.

**UX — 폼으로 사용자를 막지 않는다 (2026-08-05, 호갱노노 사이드바 분석)**

호갱노노는 사이드바 안에 이미 보유세 계산기를 갖고 있다
([hogangnono-analysis.md §8](./hogangnono-analysis.md)). 가져올 패턴 셋:

1. **기본 가정을 한 줄 문장으로 보여주고 `[변경]`으로만 폼을 연다.**
   `개인, 1인 소유, 1주택, 60세 미만, 1년 보유  [변경]`
   첫 화면에서 입력을 요구하지 않는다. 바꿀 사람만 연다
2. **연도별 시계열 표.** 과거 실적과 예상을 한 표에. 공시가 옆에 현실화율 병기
3. **미래 가정을 파라미터로 노출.** 그쪽은 `공시지가 예상 증감률 31%` — 순수 복리
   가정이고 숨기지 않는다 (검산: 18.17억 × 1.31 = 23.8027억 ✓)

**공시가격 기본값.** 동·호까지 받는 결정은 유지한다 — 층·향 보정으로 호별 공시가격이
다르고 세액이 달라진다. 다만 **평형 대표값을 입력 전 추정치로 먼저 보여주고**, 동·호가
들어오면 정밀값으로 대체한다. 1번과 같은 원리다.

**골든 케이스 추가 — 호갱노노 대조**

호갱노노 은마 76.79㎡ 화면에 조건이 전부 명시돼 있다 (1주택·단독명의·60세 미만·1년 보유):

| 년도 | 공시가 | 재산세 | 종부세 | 합계 |
|---|---|---|---|---|
| 2025 | 18억 1,700 (67%) | 344만 | 176만 | 520만원 |

라벨은 `2025/01 기준`이고 개편안은 2026-08-03 발표라 **개편안 반영 여부는 미확인이다**
(서버 API 없음, JS 리소스 35개에 세법 상수 문자열 0건). 우리 P0 엔진에 **현행법으로**
같은 입력을 넣어 대조하면 (a) 그쪽 세법 버전과 (b) 우리 엔진의 실서비스 일치 여부가
동시에 확인된다. propertytax.co.kr에 쓴 방법과 같다.

**검증**
- 다주택 합산이 골든 케이스와 일치
- 종부세 기본공제 `4억 + 5억 × (거주주택 ÷ 합계)`가 정확히 적용
- 일부 주택의 공시가격이 없으면 **계산하지 않고** 어느 건이 왜 없는지 알린다 (R4-b)
- 과세표준·적용세율·공제액 등 중간값이 함께 표시된다
- 위 은마 케이스가 현행법 기준으로 호갱노노와 일치 (불일치 시 원인을 규명하고 기록)

**선행** P0, P2, P3

## P8 — 토지·상가 + 자산 유형 좌측 사이드바

**목표** 주택 외 자산으로 범위를 넓힌다. **A안에 따라 주택 3단계(P4·P5·P9) 완결 후 착수.**

**자산 유형 좌측 사이드바가 여기서 들어온다.** 그전에는 탭이 주택 하나뿐이라 의미가 없다.
단순 필터가 아니라 **탐색 방식·세목 조합·데이터 원천이 모두 갈리는 모드 스위처**다
([product-vision.md §6.3](./product-vision.md)).

지금 지도 위에 떠 있는 검색(`src/app.css`의 `.app-shell__search`, `position: absolute`)을
좌측 사이드바로 끌어내리는 작업이 함께 간다. **주택만 "지도 우선"이고 토지·상가는
"검색 우선"이라** 그 관계가 뒤집히기 때문이다.

### 왜 별도 Phase인가

주택과 **세목 자체가 다르다.** 기존 계산에 자산 유형만 추가하면 되는 일이 아니다.

| | 주택 (P0~P7) | 상가·토지 (P8) |
|---|---|---|
| 재산세 과세 기준 | 주택 공시가격 | 건물분 시가표준액 + 토지분 개별공시지가 |
| 종부세 | 주택분 (합산) | 건축물은 **대상 아님**. 토지분은 별도 체계 |
| 양도세 장특공제 | 장기**거주**소득공제 | 장기**보유**소득공제 (개편안 p56 이원화) |
| 비과세 | 1세대1주택 12억 | 해당 개념 없음 |

**토지 3분류 판정**(종합합산 / 별도합산 / 분리과세)이 새로 들어온다. 실무에서 가장
까다로운 부분이며, 이 판정을 틀리면 세액이 통째로 어긋난다.

### 개편안이 토지에 대해 정한 것

| 항목 | 내용 | 시행 |
|---|---|---|
| 비사업용 토지 장특공제 (p95 ①) | **적용 배제** — 배제자산에 추가 | '28.1.1. 양도분~ |
| 비사업용 토지 양도세 (p95 ②) | 기본세율 +10%p → **+20%p** | '28.1.1. 양도분~ |
| 종합합산 토지 종부세 (p96 ④) | 45억 초과 구간 3% → **4%**<br>(15억 이하 1% / 15~45억 2%는 유지) | '28.1.1. 성립분~ |
| **별도합산 토지** (상가·공장·물류시설 부지) | **개편 없음 (좌동)** | — |

> ⚠️ **p96의 별도합산 세율표는 PDF 텍스트 추출이 깨져 있다.**
> ("200억 이하 0.5% / ~~15억 초과 45억 이하 0.6%~~ / 400억 초과 0.7%" — 가운데 행이 명백한 오류)
> 구현 전 **원문을 눈으로 확인**하고 `tax-rules-spec.md`에 정확히 옮길 것.

> **상가는 개편 효과가 거의 없다.** 부속토지가 별도합산이고 그 세율은 개편 대상이 아니며,
> 건축물분 재산세도 개편이 없다. "개편 전후 비교"라는 이 서비스의 핵심 가치가
> 상가에서는 나오지 않는다는 뜻이다. 착수 판단 시 고려할 것.

### UX 문제 — 지도로는 안 된다

아파트는 단지 하나에 마커 하나지만 **토지는 필지 단위라 전국 수천만 필지**다.

## P9 — 취득세 (주택)

**목표** 3단계의 첫 단계. **A안에 따라 P5(양도세) 다음, P6(시뮬레이션) 앞에서 실행한다.**
번호가 뒤인 것은 나중에 신설했기 때문이고, 순서는 위 Wave 표를 따른다.

**왜 지금까지 없었나.** 로드맵을 보유세→양도세로 짰을 때 취득세를 범위에 넣지 않았다.
`260804 3단계프로그램.xlsx`의 시트 구성(취득·보유·처분)이 최종 형태임이 확인되면서
**3단계 중 1단계가 통째로 빠져 있었다는 것이 드러났다**
([product-vision.md §3](./product-vision.md)).

**산출물**
- `src/rules/acquisition/` — 취득세·지방교육세·농어촌특별세 (P0 룰 엔진과 같은 규칙)
- `docs/tax-rules-spec.md`에 취득세 절 추가 — **여기가 먼저다.** 값의 SSOT
- `docs/golden-cases.md`에 취득세 케이스 추가

**세율 구조** (엑셀 `취득` 시트 기준. 구현 전 법령 원문으로 검증할 것)

```
주택 유상취득
  6억 이하           1%
  6억 초과 ~ 9억     (취득가액 × 2/3억 − 3) / 100        ← 선형보간. 구간 판정이 아니다
  9억 초과           3%
  2주택 · 조정대상지역   8%
  3주택 · 조정 12% / 비조정 8%
  4주택 이상            12%
상속 2.8%   무상(증여) 3.5%
농지 3%   자경농지 1.5%   그 외(상가·오피스텔·토지·건물) 4%

+ 지방교육세    주택 유상취득은 **취득세액의 10%**, 그 외는 자산별 정률
+ 농어촌특별세  전용면적 **85㎡ 초과**에 0.2%
```

> **6~9억 구간이 선형보간이다.** 계단식 구간표가 아니라 취득가액의 연속 함수다.
> 다른 세목의 누진 구조와 형태가 달라 **같은 테이블 추상화에 억지로 넣지 말 것** (R1).

**주의**
- **취득세는 지방세다.** 국세인 종부세·양도세와 근거 법령(지방세법)이 다르다.
  `tax-rules-spec.md`에 옮길 때 출처를 개편안 PDF가 아니라 **지방세법 조문**으로 단다
- 2026 세제개편안에 취득세 개편이 포함되는지 **먼저 확인**한다.
  없다면 "현행 vs 개편안" 비교 화면이 취득 단계에는 나오지 않는다
- 자산 유형별 세율이 이미 갈린다(주택 1~12% / 농지 3% / 자경농지 1.5% / 그 외 4%).
  **P8의 자산 유형 확장을 여기서 미리 만들지 않는다.** 주택 경로만 구현하고,
  나머지는 타입에 자리만 둔다 (AGENTS.md §4 과잉 추상화 금지)

**검증**
- 골든 케이스와 일치. 특히 **6~9억 경계**(정확히 6억 / 6억 1원 / 9억 / 9억 1원)
- 85㎡ 경계에서 농어촌특별세가 켜지고 꺼진다
- 취득세·지방교육세·농어촌특별세가 **각각** 표시된다 (합계만 내지 않는다)

**선행** P5

## 확정된 결정

- **확장 순서 — A안: 깊이 우선 (2026-08-05).**
  **주택 하나를 3단계(보유 → 양도 → 취득) 끝까지 끝낸 뒤** 토지·상가로 넓힌다.
  너비 우선(보유세를 주택→건축물→토지로 먼저 넓히기)은 채택하지 않는다.
  주택 사용자에게 완결된 가치를 먼저 주는 쪽을 택했다.
  → 자산 유형 좌측 사이드바는 **P8과 함께** 간다. 그전에는 탭이 하나뿐이라 의미가 없다
  ([product-vision.md §6.3](./product-vision.md))
- **주변 편의시설 검색 — 넣지 않는다.** 세금 계산과 무관하고, 기존 서비스처럼
  지도 `idle` 이벤트마다 호출하면 카테고리 장소 검색(2원/건)이 지도 SDK(0.1원/건)보다
  먼저 쿼터를 소진한다
- **지도 라벨 — 단지명** (2026-08-04 변경). 처음에는 실거래가로 정했다가 뒤집었다:
  라벨에 가격을 띄우면 지도 이동마다 약 117회 호출이 필요해 일일 한도 10,000을
  85번 이동에 소진한다. **실거래가는 사이드바에서 단지 하나를 열 때만 조회한다.**
  축소 시 라벨은 법정동 집계다 (P2-3)
- **디자인 — WhereIsMyHome은 시각적 레퍼런스일 뿐 코드를 복사하지 않는다.**
  라이선스가 없어 HTML·CSS도 저작권 대상이다. 레이아웃 개념은 참고 가능하지만
  마크업·CSS·클래스명·자산은 복사 금지. Bootstrap 4 + bootstrap-vue 2(Vue 2 전용)라
  React에서 동작하지도 않는다. 스크린샷을 보고 새로 만든다
