# 호갱노노 분석

> 2026-08-05 조사. 네트워크 계층은 브라우저에서 직접 관측했고, 수치는 전부 실측이다.
> 지도 SDK 사용법은 [kakao-map-reference.md](./kakao-map-reference.md)가 SSOT다.
> 이 문서는 **경쟁 서비스가 무엇을 하는가**와 **우리 계획이 무엇을 바꿔야 하는가**만 다룬다.

---

## 0. 결론 먼저

| 발견 | 우리 계획에 미치는 영향 |
|---|---|
| 축소 시 **법정동 단위 서버 클러스터** (`청담동 24.5억`) | **바꾼다** — `123개 단지` → `청담동 18단지` |
| bbox 응답에 단지 레코드 전체를 실음 (3.4KB/단지) | **규칙으로 못 박는다** — 라벨 응답은 최소 필드만 |
| 베이스 지도가 이미 단지명을 그린다 | 확인만. 우리 라벨은 클릭 대상이라 중복이 아니다 |
| `pnu`, `도로명주소_관리번호`, `type_official_price` 보유 | 우리 P3 설계가 업계 관행과 같음을 확인 |
| **주소가 색인돼 있지만 번지로는 단지가 안 나온다** | 우리 정확 매칭이 실제로 낫다 — §7 |
| **사이드바에 보유세 계산기가 이미 있다** | P4 설계에 직접 반영 — §8 |
| 평형별 **공시가격 20년 시계열** 보유 | P3·P6에 직접 반영 — §8.3 |

## 1. 아키텍처 — r114와 같은 bbox 모델

호갱노노도 **지도 이동 → bbox 질의**다. r114(`api.propx.co.kr/props/gis`)와 동일한 구조로,
D1 bbox 인덱스를 쓰기로 한 우리 결정을 다시 확인해 준다.

```
GET /api/apt/bounding
    ?map=google&level=17&screenWidth=899&screenHeight=863
    &startX=127.0499689&endX=127.0596141      ← 경도 범위
    &startY=37.5193312&endY=37.5266746        ← 위도 범위
    &tradeType=0&areaFrom=0&areaTo=50&priceFrom=0&priceTo=500000
    &gapPriceFrom=..&sinceFrom=..&floorAreaRatioFrom=..&buildingCoverageRatioFrom=..
    &rentalBusinessRatioFrom=..&householdFrom=..&parking=..&profitRatio=..
    &rentRateFrom=..&aptType=-1&auctionState=-1&reconstructionStep=..
```

관측된 다른 엔드포인트:

| 엔드포인트 | 역할 |
|---|---|
| `/api/apt/bounding` | 단지 마커 **또는** 클러스터 (레벨에 따라) |
| `/api/v2/pois-bounding` | 지하철역·마트·병원 등 주변 POI — **우리 범위 밖** (사용자가 제외함) |
| `/api/v2/maps/region?lat&lng&zoom` | 현재 중심의 행정구역 |
| `/api/v2/ads/markers/store/bounding` | 광고 마커 |
| `/api/v2/activity-logs/collect` | 행동 로그 |

**필터 20여 개가 전부 같은 bbox 호출에 실린다.** 서버 사이드 필터링이다.
우리 사이드바 필터(전용면적·거래연도)는 온디맨드로 받은 소량에 대한 클라이언트 필터이고,
그 규모에서는 그게 맞다. 이 필터 표면을 따라갈 이유는 없다.

> 재현 불가 주의 — `x-hogangnono-at`/`ct` 서명 검증이 있어 캡처한 헤더로 재요청하면 400이다.
> 아래 수치는 전부 **페이지 자신의 XHR을 가로채** 얻었다.

## 2. 핵심 발견 — 축소 시 법정동 클러스터

같은 엔드포인트가 레벨에 따라 **다른 종류의 객체**를 돌려준다.

| 지도 레벨 | `poiType` | 실측 n | 실측 크기 |
|---|---|---|---|
| 16 (확대) | `"apt"` | 150 | **501.8 KB** |
| 15 | `"cluster"` | 2 | 2.1 KB |
| 14 (축소) | `"cluster"` | 14 | 14.2 KB |

클러스터 레코드는 **법정동 집계**다 (`region_code`가 법정동코드 앞 8자리):

```json
{
  "id": 463, "region_code": "11680104", "poiType": "cluster",
  "lat": 37.525083, "lng": 127.0493,
  "real_trade_price": 244933,          // 24.49억 — 동 평균 실거래가
  "content": {
    "name": "서울특별시 강남구 청담동", "shortName": "청담동",
    "length": 110,                      // 동 내 단지 수
    "totalHousehold": 9088, "floorAreaRatio": 317.525,
    "officetel": { "real_trade_price": 105580, "length": 15 }
  },
  "realtime": { "visitor": 147, "rank": 7 }
}
```

화면에서는 이렇게 보인다:

```
확대 (레벨 16+)              축소 (레벨 15-)
 ┌────────┐                  ┌──────────┐
 │  34평  │  ← 집 모양 핀     │  청담동   │  ← 사각 라벨
 │ 27.3억 │                  │  24.5억   │
 └───▼────┘                  └──────────┘
```

**핵심은 클러스터에 이름이 있다는 것이다.** `12개 단지`는 위치 정보를 주지 못하지만
`청담동`은 준다. 축소 상태에서 사용자가 실제로 하는 일 — "우리 동네 어디였지" — 에
직접 답한다.

## 3. 우리가 바꿀 것

### 3.1 클러스터 라벨을 법정동 단위로 — **바꾼다**

현재 `src/map/ComplexMap.tsx`는 카카오 `MarkerClusterer`에 `${count}개 단지`
(`src/messages/map.ts:2`)를 붙인다. 좌표 근접도로만 묶으므로 이름이 없다.

우리는 이미 `complex.legal_dong_code`(10자리, NOT NULL, 인덱스 있음)를 갖고 있다.
**추가 외부 호출 0회**로 동 단위 집계가 된다.

같은 bbox(호갱노노 레벨 14 뷰포트)에 대한 실측:

| | 값 |
|---|---|
| 우리 bbox 안 단지 수 | 254 |
| 법정동으로 묶으면 | **24개 라벨** |
| 상위 | 자양동 45 · 삼성동 26 · 역삼동 24 · 논현동 19 · 대치동 19 · 청담동 18 |
| 전국 법정동 수 (단지 보유) | 3,042 |

```sql
SELECT legal_dong_code, COUNT(*) AS n, AVG(lat) AS lat, AVG(lng) AS lng
  FROM complex
 WHERE lat BETWEEN ?1 AND ?2 AND lng BETWEEN ?3 AND ?4
 GROUP BY legal_dong_code
```

**단, 라벨에 가격은 넣지 않는다.** 동 평균 실거래가를 표시하려면 실거래가를 적재해야
하는데, 우리는 사이드바 온디맨드로 확정했다(`docs/roadmap.md` 확정된 결정). 라벨은
`청담동 18단지` — 이름 + 단지 수까지다.

**동 이름을 어디서 얻는가.** 현재 `complex` 테이블에 동 이름 컬럼이 없다. 두 경로가 있다:

| 방법 | 비용 | 정확도 |
|---|---|---|
| `legal_address` 문자열 파싱 | 0 | **99.7%** — 2,971개 코드 중 2,963개가 이름 1개로 확정. 나머지 8개는 코드와 주소 문자열이 어긋나는 경계 데이터 |
| 지오코딩 시 `region_3depth_name` 저장 | 0 (이미 호출 중) | 100% |

**후자를 택한다.** `scripts/lib/kakao-complex-search.ts:138`의
`parseKakaoLegalDongCodeResponse`는 지금 `code`만 뽑고 `region_3depth_name`을 버린다.
같은 응답에 이름이 이미 들어 있다. 프로덕션 D1은 아직 비어 있어 적재를 한 번 더
돌려야 하므로, 지금 필드를 추가하면 **추가 API 호출이 0**이다. 파싱 휴리스틱을
코드에 남기지 않는 쪽이 R2(하드코딩 제거)에도 맞다.

### 3.2 bbox 응답 페이로드 최소화 — **규칙으로 못 박는다**

호갱노노는 마커 하나에 44개 필드 + 51개 필드짜리 `area` 객체를 통째로 보낸다.
**단지당 3,425 B**, 레벨 16 한 화면에 **501.8 KB**. 라벨을 그리는 데 필요한 건
이름과 좌표뿐인데도 그렇다.

우리 `worker/complex/bbox.ts:83`은 10개 필드를 보낸다. 같은 뷰포트 실측:

| | n | 크기 | 단지당 |
|---|---|---|---|
| 호갱노노 (레벨 16) | 150 | 501.8 KB | 3,425 B |
| **우리 현재** (10필드) | 254 | 83.8 KB | 329 B |
| **최소 4필드** (`complex_id, name, lat, lng`) | 254 | **29.2 KB** | 115 B |

이미 10배 이상 가볍지만 **65% 더 줄일 수 있다.** 사이드바는 어차피
`worker/complex/catalog.ts`로 상세를 따로 받는다 — bbox 응답의 나머지 6개 필드는
지금 아무 데도 안 쓰인다.

### 3.3 오버레이 일괄 숨김 — **작은 추가**

호갱노노 우측에 `숨김` 버튼이 있다. 한 번 누르면 라벨·POI·광고가 전부 사라지고
베이스 지도만 남는다. 라벨이 조밀한 지역에서 실제로 쓸모가 있고, 우리 구현 비용은
`labelsVisible` 상태 하나다. P4 이후 여유가 있을 때 넣는다.

## 4. 바꾸지 않을 것 (확인만)

**베이스 지도가 이미 단지명을 그린다.** 네이버 타일에 `청담자이아파트`,
`청담삼익아파트`가 이미 찍혀 있다. 카카오도 같다. 그래서 호갱노노 핀은 이름 대신
`{평}{가격}`을 쓴다 — 중복을 피한 것이다.

우리 라벨은 단지명이므로 형식상 겹친다. 그래도 바꾸지 않는다:
베이스 지도 라벨은 **클릭할 수 없고**, 우리 라벨은 사이드바를 여는 유일한 진입점이다.
다만 클릭 가능해 보이게 시각적으로 확실히 구분되어야 한다는 근거는 된다.

**주변 POI (`pois-bounding`).** 사용자가 명시적으로 제외했다. 유지.

**`realtime.visitor` — "147명 보는중".** 로그인·분석 백엔드가 필요하고 세금 계산과
무관하다. 제외.

## 5. 세금 데이터 측면에서 확인된 것

호갱노노 단지 레코드가 우리 P3 설계와 같은 축을 쓴다:

| 그들의 필드 | 우리 대응 |
|---|---|
| `pnu` | P3 주소→PNU |
| `도로명주소_관리번호`, `도로명주소_코드` | 도로명주소 매칭 |
| `area.type_official_price` | **P3 공시가격** — 평형별 |
| `area.type_official_price_increase_ratio` | 공시가격 변동률 |
| `area.private_area` / `public_area` | 전용/공급면적 |
| `area.real_trade_price` / `max_real_trade_price` | P1 실거래가 |

**공시가격을 단지×평형 단위로 들고 있다.** 우리 P3이 목표하는 입도와 같다.
그들은 이걸 시세 비교용으로 쓰지만, 우리는 그게 보유세 과세표준 그 자체다.

`area`는 대표 평형 **하나만** 온다(`is_major: 1`). 라벨에 쓸 값이라 그렇다.
우리는 보유세 계산에 사용자가 소유한 평형이 필요하므로 이 축약을 따라갈 수 없다.

## 7. 검색 — 주소는 색인돼 있으나 번지로는 못 찾는다

플레이스홀더는 "아파트, 지역 또는 학교명으로 검색"이지만 **주소도 색인돼 있다.**
`/api/v2/searches/suggestions/new?query=&x=&y=` (`x`/`y`는 지도 중심 — 근접도 가중).

응답 문서를 보면 Elasticsearch류 다중 필드 색인이다:

```
name_analyzed        "대치동 3 차 풍림 아이원"        ← 형태소 분석
name_bigram / name_space / name_korean
address_analyzed     "서울 특별 시 강남 대치 1007-1"
address_bigram / address_space
road_address_bigram  "영동대로72길 10"
apt_total            주소 + 분석주소 + 도로명 + 단지명을 이어붙인 catch-all
rank_point           1.032, 1.003, ...
tag                  "명문학군 대현초 양재천 역세권 남향 ..."   ← 큐레이션 태그
```

**그런데 실제로는 주소로 그 단지를 못 찾는다.** 은마아파트(서울 강남구 대치동 316 /
삼성로 212)로 검증했다:

| 질의 | 은마 나오나 | 실제 상위 결과 |
|---|---|---|
| `은마` | ✅ 1위 | 은마 / 대치동 316 |
| **`대치동 316`** (정확한 지번) | ❌ **없음** | 대치동3차풍림아이원(1007-1), 대치동부센트레빌(670), **그린빌16단지(안산)**, **명지캐럿162(안양)** |
| **`삼성로 212`** (정확한 도로명) | ❌ **없음** | 삼성팰리스, 삼성루첸시아 — 전부 삼성**동** |
| `서울 강남구 삼성로 212` | ❌ 더 나빠짐 | 수서동 삼성, 도곡동 현대비젼21 |
| `대치동` (동명) | — | 대치동 단지들 ✅ + `region` 카테고리에 "서울특별시 강남구 대치동" |

번지 토큰(`316`, `212`)이 관련도에 거의 기여하지 못한다. `316`의 `16`이 **안산
그린빌16단지**를 끌어올 정도다. `rank_point`가 전부 1.00x대인 것도 변별이 없다는 뜻이다.

**즉 "주소 토큰이 색인돼 있다" ≠ "주소로 단지를 찾을 수 있다".**
동·지역명 검색은 잘 되고(`region` 카테고리 별도 존재), 번지 단위 해석은 안 된다.

우리 구현은 D1 정확·접두 매칭이라 `대치동 316` → 은마가 나온다(P2에서 브라우저로 확인).
**이 부분은 우리가 낫다. 유지한다.**

**가져올 것 — 중복 단지명 구분 표기.** 제안 목록이 `{동명} {단지명}` 형식이다:

```
대치동 은마       ← 서울 강남구
덕천동 은마       ← 부산 북구
서신동 은마       ← 전주 완산구
구암동 은마       ← 창원 마산회원구
```

전국 단지명은 중복이 흔하다. 우리 검색 결과도 단지명만 보이면 어느 은마인지 알 수 없다.
**동명을 앞에 붙인다** — `legal_dong_code`로 얻는 동명(§3.1)을 그대로 쓴다.

## 8. 사이드바 — 보유세 계산기가 이미 있다

`/apt/{aptId}/{areaNo}` 로 URL이 바뀐다. **단지 + 평형이 URL에 들어간다** — 공유·북마크
가능. 우리는 지금 사이드바 상태가 URL에 없다. 나중에 볼 일이다.

패널 스크롤 높이 **12,221px / 화면 652px — 18.7배**다. 사용자가 "스크롤이 너무 길지
않으면 좋겠다"고 한 바로 그 문제다. 우리 탭 분리 결정이 옳았다.

섹션 순서: 헤더(주소·세대수·연차·용적률·건폐율) → 3D 단지투어 → 실시간 방문자 →
토지거래허가 → **가격 차트** → **실거래 목록** → 매물 → 뉴스 → 지역 평당가 비교 →
재건축 현황 → 경매 → **거래세·보유세** → 타입/동 정보.

### 8.1 보유세 섹션 (실측 — 은마 76.79㎡)

```
거래세
  예상 거래가  34억 6,000
  세금         1억 1,418만원
  중개보수 0.7%   2,422만원

보유세                                   2025/01 기준
  101타입
  개인, 1인 소유, 1주택, 60세 미만, 1년 보유    [변경]
  [보유주택 추가]
  공시지가 예상 증감률   31%
```

**가져올 것 세 가지.**

1. **조건을 한 줄로 압축하고 `[변경]`으로 연다.**
   "개인, 1인 소유, 1주택, 60세 미만, 1년 보유" — 기본 가정을 문장으로 보여주고
   바꾸고 싶을 때만 폼을 연다. 계산기가 폼으로 사용자를 막지 않는 방법이다.
   **P4의 기본 UX로 채택한다.**

2. **연도별 시계열 테이블.** 과거 실적(2023–2025)과 예상(2026–2027)을 한 표에.
   공시가 옆 괄호는 현실화율(72%, 67%). 세액만 던지지 않는다는 우리 §4 계산 결과
   규약과 같은 방향이다.

3. **미래 가정을 파라미터로 노출.** `공시지가 예상 증감률 31%`.
   검산: 18.17억 × 1.31 = **23.8027억** ✓ / 23.8027 × 1.31 = **31.1815억** ✓.
   순수 복리 가정이다. 숨기지 않고 사용자가 만질 수 있게 뒀다.

### 8.2 우리와 무엇이 다른가 — 축이 다르다

> **호갱노노는 공시가격을 움직이고 세법을 고정한다.
> 우리는 세법을 움직인다 (현행 vs 2026 개편안).**

라벨이 `2025/01 기준`이고, 개편안은 **2026-08-03 발표 — 이틀 전**이다.
보유세 계산은 서버 API도 아니고 로드된 JS 청크에도 세법 상수가 없어(전수 확인:
JS 리소스 35개에 `종합부동산세`·`공정시장가액`·`재산세` 문자열 0건) 어디서 나오는지
특정하지 못했다. **개편안 반영 여부는 미확인이다** — 추정하지 않는다.

**검증 방법이 있다.** 위 2025년 행(공시가 18억1,700 → 재산세 344만 / 종부세 176만)은
1주택·단독명의·60세 미만·1년 보유라는 조건이 전부 명시돼 있다. 우리 P0 엔진에
현행법으로 같은 입력을 넣어 대조하면 (a) 그쪽이 현행법인지, (b) 우리 엔진이 실서비스와
일치하는지 **둘 다** 확인된다. propertytax.co.kr로 이미 쓴 방법이다
([golden-cases.md](./golden-cases.md)). **P4 착수 시 골든 케이스로 추가한다.**

### 8.3 공시가격 — 평형별 20년 시계열을 들고 있다

`/api/apt/{id}/detail`의 `currentArea`:

```json
"type_official_price": 181700,
"date_official_price": "2024-12-31",
"type_official_price_data": {
  "2005": 57600, "2010": 72500, "2015": 67900, "2020": 155100,
  "2021": 185000, "2022": 133200, "2023": 159400, "2024": 181700
},
"type_real_price_per_official_price_data": {
  "2024": 0.666, "2023": 0.673, "2022": 0.718, "2021": 0.743
},
"type_official_price_increase_ratio": 0.144
```

은마 평형별 (단위 만원):

| 평형 | 전용 | 공급 | 세대 | 실거래 | **공시가격(2024)** |
|---|---|---|---|---|---|
| 0 | 76.79㎡ | 101.52㎡ | 2,674 | 346,000 | **181,700** |
| 1 | 84.43㎡ | 115.54㎡ | 1,750 | 390,000 | **210,300** |

**공시가격을 단지 × 평형 단위로 제공한다.** 동·호는 받지 않는다.

우리는 동·호까지 받기로 했다(사용자 결정) — 실제 공시가격은 층·향 보정으로 호별로
다르고, **세액이 달라지므로** 세금 계산기에서는 그 정밀도가 필요하다. 그 결정은 유지한다.

**다만 평형 대표값을 기본 추정치로 쓸 수 있다.** 동·호를 입력하기 전에도 "이 평형이면
대략 이 정도"를 보여주고, 동·호가 들어오면 정밀값으로 대체한다. 첫 화면에서 사용자를
입력 폼으로 막지 않는 방법이고, §8.1의 1번과 같은 원리다.

`type_real_price_per_official_price_data`(현실화율 시계열)는 **P6 시뮬레이션의 근거
데이터**가 된다 — 미래 공시가격을 추정할 때 임의의 숫자 대신 과거 현실화율 추이를 쓴다.

### 8.4 실거래 목록·차트 — 우리보다 한 겹 더 있다

```
GET /api/v2/apts/{id}/trade-real?tradeType=0&start=0   → 개별 거래 (페이징)
GET /api/v2/apts/{id}/monthly-reports?tradeType=0&areaNo=0  → 월별 집계
```

`monthly-reports` 응답에 **이상치 처리가 실려 있다**:

```json
{ "includeAuction": false, "includeLowerFloor": false, "includeOutliner": false,
  "shortTermReport": [{ "date": "2023-08-31", "minPrice": 220000, "maxPrice": 244000,
    "averagePrice": 233900, "volume": 5,
    "trades": [{ "price": 235000, "floor": 2, "isLowerFloor": true,
                 "chartInReason": 1, "reasonPrice": 231000, "isInChart": true }] }] }
```

화면 안내문: *"저층이기 때문에 평균 계산에서 제외됐습니다. 최고층이 10층 미만은 1층,
10층 이상은 3층까지를 저층으로 판단합니다."*

**우리 연도별 평균가 차트는 지금 전 거래를 단순 평균한다.** 저층·경매·이상치가
그대로 섞인다. 규칙을 정하든 안 정하든 **평균의 정의를 화면에 밝혀야 한다.**
호갱노노처럼 토글까지 줄 필요는 없지만, "무엇을 평균했는가"는 세금 계산기에서
더더욱 숨기면 안 된다. `isCancelled`(해제 거래) 필드는 우리도 이미 처리 중이다.

### 8.5 안 가져올 것

`/api/apt/{id}/detail` 한 방에 **176 KB**, 최상위 키 90개. 리뷰·매물·뉴스·경매·학군·
통근·배송생활권·설문까지 전부 한 응답이다. 사이드바 열 때 API 11개가 동시에 나간다.
§3.2의 bbox 페이로드 문제와 같은 병이며, 상세 화면에서 더 심하다.

3D 단지투어 · 리뷰/사진 · 매물 · 뉴스 · 경매 · 재건축 단계 · 학군 · 통근 ·
배송생활권 · 설문 — 전부 우리 범위 밖이다.
